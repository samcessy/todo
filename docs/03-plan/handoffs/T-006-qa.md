## Decisions made inside the task scope
- **Appearance.** The kit reads the `appearance` cookie (`HandleAppearance` → `app.blade.php`) and defaults to `system`, which follows `prefers-color-scheme`. The plugin has no cookie API, so the test leaves the cookie unset and uses `visit()->inLightMode()` / `->inDarkMode()`, then asserts `<html>` has (or lacks) the `dark` class. Explicit `light`/`dark` cookie values are not scanned separately; they render the same class.
- **`settings/security`** requires password confirmation (`RequirePassword`). The test goes through `/user/confirm-password` with the factory password, then scans `/settings/security`. The confirm page itself is not in ADR-0003's list, so it is not scanned; a probe shows the same `landmark-one-main` + `region` findings as the other auth-layout pages.
- **Waiting for animations.** `assertNoAccessibilityIssues()` waits for `networkidle` but not for CSS transitions. Without a wait, the welcome page's `@starting-style` fade gave false contrast failures (1.04:1 mid-fade). The test awaits `document.getAnimations()` before the scan. This makes the scan see the final page; it does not loosen it.
- **Role locators.** `press('Confirm password')` clicked the auth layout's logo link (its sr-only text matches) and `press('Delete account')` hit the section heading. Tests use `internal:role=button[name="…"s]` (Playwright role selector, exact name), which also matches test-strategy §6.
- **Tab fact uses a fixture.** The Tab/Shift+Tab test injects three inputs, so it does not depend on the kit's positive tabindex (finding F-3), which the vue-engineer will remove.
- **Sessions.** The array session driver from `phpunit.xml` keeps sessions across in-process browser requests (password confirmation persists), so no driver override is needed.

## Addendum (2026-11-18): appearance-toggle contrast finding

A manual Lighthouse audit (axe-core 4.14) found a WCAG 2.2 AA 1.4.3 failure that the plugin's axe-core 4.10.3 scan missed, so `CC.AC1 has no accessibility issues…` stayed green.

| ID | Check | Page | Element(s) | Light | Dark | Owner |
|---|---|---|---|---|---|---|
| F-6 | Direct contrast (`color` vs first non-transparent ancestor `background-color`) | `/settings/appearance` | Appearance toggle labels; inactive "Light" and "Dark" (with "System" selected) render neutral-500 (`#737373`) on the group's neutral-100 (`#f5f5f5`) | "Light" 4.349, "Dark" 4.349, "System" 19.80: **fails** | "Light" 5.857, "Dark" 5.857, "System" 9.51: passes | vue-engineer (appearance toggle component; QA did not read `resources/`) |

- **Test:** `tests/Browser/AccessibilityTest.php` → `CC.AC1 appearance toggle labels meet 4.5:1 contrast in light and dark mode` (dataset `appearances`). It finds the group through its buttons' accessible names, computes the ratio for every button (active and inactive) in `script()`, and converts colours through a canvas because the computed values are `oklch()`. Red commit `0c9593a4`. It fails on light only, with "Light" and "Dark" at 4.349:1 (Lighthouse rounds this to 4.34). That matches the Lighthouse values, so the test fails for the right reason.
- **Observation, not tested:** the toggle group has no role or accessible name, and the buttons expose no selected state (`aria-pressed` or a radio group). A screen reader cannot tell which appearance is active. This is outside 1.4.3. Vue-engineer or owner to decide whether CC.AC1 covers it.
- **Process:** `test-strategy.md` §6 now records the axe version lag. Controls whose colours are near the threshold, or that an audit flags, get a direct contrast assertion, and the G5 manual Lighthouse pass (NFR-06) stays mandatory. Revisit when the plugin updates axe.
