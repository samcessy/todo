## 1. Assets and actors
| Asset | Why it matters |
|---|---|
| Todo content (free text, may contain personal data) | Confidentiality between users (NFR-02, Goal 2) |
| Accounts: email, password hash, 2FA secret, recovery codes, passkeys | Account takeover |
| Session cookie, CSRF token | Impersonation |
| `APP_KEY`, `PASSKEYS_USER_HANDLE_SECRET`, DB credentials, deploy hooks | Full compromise or an unreviewed release |
| Repo `main`, workflows and CI gates | The integrity of the process (governance) |
| Third parties' mailboxes, the sender reputation, HIBP and CPU budget | Abuse of public endpoints that send mail (B-04) |

| Actor | Capability |
|---|---|
| Anonymous internet user | Reaches public routes on staging and production (Starter has no basic auth, ADR-0006). Can read the public repo and open fork PRs |
| Authenticated user | A valid session and their own todos. Might try to reach other users' data |
| AI agent (Claude Code subagents and main thread) | Shell in the repo, bot GitHub identity with a token that cannot write workflows (G1-1, G2-5). Could be confused, prompt-injected or over-eager |
| Owner | All rights. Holds the production hook (G1-2) and the repo admin role |

## 2. Threat model
"Verified by" names the deterministic control: a test, a CI check or a configuration assertion. "Checklist" means a T-002 setup, staging smoke or G5 go/no-go item, used only where no automated check in the PR path is possible. Every checklist item names the exact command whose output is recorded.

| T-18 | **Workflow misuse: secret exfiltration or `GITHUB_TOKEN` abuse** (B-05, G2-5). GitHub runs `push` and `pull_request` workflows **from the pushed branch's own workflow files**, and same-repo branches get secrets referenced by those files. A bot that can push a modified workflow can therefore exfiltrate secrets before any review | **(1) The bot cannot write workflows.** GitHub's docs state that fine-grained PATs cannot be used by a repository collaborator, and that only classic PATs have write access to public repos not owned by the token's user (https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens, "Fine-grained personal access tokens limitations", fetched 2026-11-17). The bot's credential is therefore a **classic PAT with only the `public_repo` scope**: it covers contents and pull requests, and it has **no `workflow` scope**, which is what GitHub requires to "add and update GitHub Actions workflow files" (https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps). No `repo`, `admin:*`, `delete_repo` or `workflow` scope; 90-day expiry; the bot is a collaborator on this repository only; **no SSH keys** on the bot account (SSH pushes are not scope-checked).
